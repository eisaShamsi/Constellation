**What a unified entry IS (resolves the base/overlay tension).** Keep BOTH semantics inside ONE `StylePreset` list (the MIG-070 §A model, already coded): a **base-coat look** is a preset whose `colorsTheme` section carries a full theme (`themeToStyle`); an **overlay look** is a saved preset carrying partial `styleOverride`/sections. The gallery shows them together; the card shows a "Theme" vs "Style" tag (`source` field, L44). Selecting a base sets `activeThemeId`; selecting an overlay merges `styleOverride` — both via `applyPreset` → `updateSettings`, so the +layout single writer composes them in its existing order (base → values → override → live). No new writer, no new compose rule.

## 3. Invariants (must not break)
- **LL-032** — Setter render path touches NO themes (no `unifiedStyleList`/`themeToStyle`/`stylePreview` cards, no `<select>`/list over `BUILTIN_THEMES`/`customThemes`). The unified gallery lives in **Settings → Appearance** (static-swatch, already safe). *(A & C satisfy by construction; B is the at-risk option.)*
- **BUG-015** — exactly ONE writer to body CSS vars: the +layout `$effect` (L1556). No second writer; the gallery only calls `updateSettings`/`applyPreset`.
- **Base + overlay composition** preserved — theme-as-base-layer then `styleOverride` overlay, in the +layout order (L1589→1629→1635).
- **Data survival** — existing `customThemes` (incl. previously imported Obsidian themes), `style-presets.json`, and `activeThemeId` keep working untouched.
- **Second-screen sync** — keep routing applies through `updateSettings` (emits `screen:settings-changed`, store.ts L4101); the second window re-runs its own single-writer apply.

## 4. Back-fill / migration / rollback
- **Migration: none required for data.** Themes + presets stay in their existing stores; `unifiedStyleList` assembles the view at READ time (L280). No schema bump, no back-fill walk (Rule 8 compliant — derived at read, not rebuilt on boot).
- **Obsidian removal** is code-only: delete `ObsidianThemeBrowser.svelte` + `obsidianImporter.ts`, remove the 4 `SettingsModal` references. `source: 'obsidian'` on stored themes is inert; leave the enum value in `ConstellationTheme` (L3060) so old themes deserialise cleanly. `'obsidian'` note-importer refs untouched.
- **First boot after update** — `applyParsedSettings` reads the same `customThemes`/`activeThemeId`; a theme whose `source` was `'obsidian'` renders identically as a custom theme. Saved styles load from the unchanged JSON file.
- **Rollback** — reverting the commit restores the Obsidian browser; no data was rewritten, so a downgrade sees its original `customThemes` + `style-presets.json` intact.

## 5. Cross-check (WA#5)
VS Code separates **Color Themes** (base) from **Settings Profiles** (overlay bundles); tweakcn/Figma keep a theme distinct from saved tweak-presets but list both in one switcher. The mature pattern is **two roles, one switcher** — exactly Option A's "unified list, tagged base-vs-overlay," which the MIG-070 §A `themeToStyle`/`unifiedStyleList` scaffold already encodes.

## 6. Recommendation
**Option A.** It reuses the already-built, non-destructive §A scaffold; the gallery lives where rendering is proven safe (Appearance, static-swatch cards); the Setter is left exactly as-is, so LL-032 cannot fire; data needs zero migration; Obsidian removal is a clean 2-file + 4-line excision. **B** only if Eisa explicitly wants the picker inside the Setter — it walks straight into the LL-032 freeze zone and must be gated behind a flat pre-resolved name list, raising risk for a convenience win. **C** is the "purist" single-store option but pays high blast-radius cost across the BUG-015 apply path and every `activeThemeId` consumer for a storage tidiness the read-time union already delivers invisibly. Recommend A; surface B/C so Eisa can choose the Setter-picker / single-store tradeoffs.
