### 1. Design pivot away from the post-§2E visual

After §2E.4 solved the Pixi GPU exhaustion and the chart finally rendered to completion, Eisa critiqued the visual outcome:

> "I am not confused about the outer rim being allocated for the calendar. What if a user has been developing their universe for several years? Find me other options. Finally, the graph doesn't resemble the original idea (the constellation celestial hemisphere)."
>
> "And the Universe Health location is a distraction. Let's take advantage of the empty spaces around the outer rim."
>
> "NO. Let's design the graph first, then the code around it if it passes. Let's identify how the circle will look like."

This forced a halt on coding and a return to whiteboard. Four mockup options drafted (Polar grid / Stratum rings / Hemispheric pair / Suwaidi-faithful), all on the cream Suwaidi palette. Eisa's first take was **Option D** (Suwaidi-faithful), then on second thought adapted **Option A** (Polar grid).

### 2. Switchable rim axis (Eisa's idea, not mine)

When I proposed Regions on the rim, Eisa pushed past it:

> "What if the user could switch between different views while viewing the graph? They can click either (B-F + Regions). Doing so will give them a hint about where their universe stands."

That single message turned Sight from a single visualization into a multi-instrument. We landed on six modes: R (Regions, default) · L (Link Types) · T (Time) · C (Confidence) · S (Stages) · A (Acts). C/S/A dimmed "available later" until the Concept Paper P2/P3/P4 data layers ship.

### 4. The (X, Y, Z) per-mode architectural pivot

Mid-§2G.3c, Eisa redirected at a higher altitude:

This elevated the spec from "rim axis only" to "azimuth + radius + magnitude per mode, color invariant." I drafted six (X, Y, Z) tuples — one per mode — anchored in each mode's diagnostic question. Eisa: **"All Approved"**.

## Patterns / lessons

1. **The implementation cascade is seductive.** Once a plan is approved, momentum makes commit / push / doc work feel like overhead. The SO discipline exists *exactly* because that feels like overhead. Skip it and the working tree carries hours of orphan work that vanishes with one process crash.

2. **Eisa reads screenshots more carefully than I do.** Twice this session he spotted issues I'd missed: the tan polygon hiding stars, the rim auto-shift from Regions to calendar months, the Arabic RTL failure. When he reports a "PASS but…", the "but" is a real bug.

3. **Architectural pivots come at higher altitudes than expected.** I was proposing the rim axis as a 1D toggle (Regions vs Time vs Link Types). Eisa elevated it to a 3D (X, Y, Z) grammar where each mode is its own diagnostic instrument. The mode-by-mode (X, Y, Z) table is the kind of design call that has to be made by the project owner — I would have shipped the simpler version and missed the cognitive depth.

4. **"Don't patch it. Solve it."** Eisa's directive earlier this evening when the OOM kept resurfacing on every patch. The §2A+§2B density-grid redesign came directly from that. Same energy in the design pivots: don't iterate the calendar rim — replace it with a switchable cognitive lens. Don't add more visual encodings — formalize them as (X, Y, Z) per mode.
