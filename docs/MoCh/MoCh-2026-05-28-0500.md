**Option H — the decisive fix.**

Added a `skip_fts5_snippet: bool` parameter to `lexical_search_in_schema`. Federated mode passes `true`: SQL selects raw `body_text` instead of calling `snippet()`. Rust then synthesizes the snippet via `synth_snippet_for_body` — a substring scan with UTF-8 char-boundary safety, handles bridge terms from lexicon expansion for cross-language matches. Active-mode unchanged.

The trade-off: federated `<mark>` placement is slightly less precise than FTS5 native (substring match vs stemmed token match). The COUNT and RANKING of results is unchanged — only the highlight position differs by a few characters in edge cases.

## Lessons (for future MIGs)

1. **When metrics plateau across 3+ iterations, dig deeper before iterating again.** Options C-G all hit ~13-16s. That was the signal to examine an entirely different dimension. SQL column-by-column was the right next move, and I should have done it earlier instead of trying more cache/Connection variations.

2. **`snippet()` with custom tokenizers is expensive.** SQLite FTS5's native `snippet()` re-tokenizes each matched row's column to find marker positions. Custom Arabic-normalizing tokenizer × 30 rows × kilobytes of body_text = ~16 seconds. Rust-side substring snippet is microseconds. Future federated-search work should default to Rust-side snippet generation unless there's a specific reason to use FTS5 native.

3. **Eisa's "no limitations" doctrine is the right operating principle.** Every "let's accept and document" framing I tried got pushed back. The actual fix existed; we just hadn't found it yet. The cost of pushing through (one more option) was always less than the cost of shipping a limitation.

4. **Diagnostic v2 was load-bearing.** Without the per-branch timings, EXPLAIN QUERY PLAN, sqlite_stat1 contents, and keystroke event log, I would have shipped Option E (which regressed) as a guess. The discipline of "data before fix" paid off across the remaining options.
