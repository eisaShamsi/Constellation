## 1. "It took 4 seconds to rename."

The block opened on a Boss test of §6e — my boot warm-up, built to remove a 2.6-second cost
from his first rename of each session. His entire report was six words. Four seconds was
**worse** than the 2,693 ms it was meant to fix.

I read his diagnostics log rather than reason about it, and it convicted my own fix
immediately: the warm-up ran, succeeded in 674 ms, and finished **three minutes** before his
rename. It had changed nothing.

**What the investigation then found** — by running `EXPLAIN QUERY PLAN` against a copy of his
live database rather than theorising:

```
SELECT DISTINCT source_path FROM note_links WHERE target_base = ?
  ->  SCAN note_links USING INDEX idx_link_source     (a full scan of 31,368 rows)
```

**The index the whole migration was built to use had never once been used.** `sqlite_stat1`
still claimed `target_base` held one distinct value across every row — true when collected
(the column was all NULL), and falsified by the very back-fill that filled it.

So PJ-249's headline result had been false for a week. It had replaced an 8.5-second file
walk with a 2.6-second table scan, and the "44 ms" second rename that made it look finished
was that same scan served from the page cache.

I reported this to the Boss plainly, including the sentence that mattered: *my §6e diagnosis
was wrong, and the fix I built for it made the symptom worse.*

## 2. "Add the instrumentation and give me a new build"

After §6f/§6g the rename came down to 1,673 ms — better, but by my own stated criterion a
**fail**, and I recorded it as one rather than presenting a 42 % improvement as success. The
remaining time had moved to the freshness net: 1,442 ms.

I told him I could not explain it — the same scan had measured 49 ms in his previous session,
same code, same folder — and that I would not guess, **because I had already guessed wrong
about that exact scan earlier the same evening**, when I was certain it was the culprit and it
turned out to be 34 ms.

His instruction was one line, and it was the right one. No debate about the theory: instrument
it and build.

That build measured the net at **71 ms** with the *same single suspect* as the slow run —
proving the suspect had never been the cause, exactly as the code had said all along — and the
whole rename at **216 ms**.
