## 1. "Do we need this?" — the Themes section

- After passing the §C-polish tests, Eisa sent a screenshot of the **Themes** section in Settings →
  Appearance and asked plainly: **"Do we need this?"**
- He explained the history himself: *"I developed this to give users the option to import themes from the
  Obsidian Community and convert them for use in Constellation. But since we developed the Style Setter, I
  don't think we need to have it."* — and floated combining **Themes** with **Saved Styles**, *"but it has
  to be all local."*
- I proposed merging the two into one all-local gallery + dropping the Obsidian import, framed as a formal
  /migration. Eisa first agreed with the merge.

## 2. The pivot — "retire it completely"

- During the first cut (MIG-071 §C made the apply path prefer the saved Style), the **built-in theme
  switching broke in testing** (clicking a theme did nothing). Eisa cut straight through the confusion:
  **"Why are we still testing the Built-in themes? It should be retired completely."**
- That reframed the whole migration: not *unify* themes with Styles, but *remove* themes outright.
- Decisions Eisa ratified, in his words:
  - **"I'd rather the cleanup just drop you onto the plain default and start fresh."**
  - **"don't keep anything"** — no backup of the wiped theme data.
  - Backup scope (when I asked): **"Only the ones in the Appearance. The Style Setter is doing better."**
  - Touch scope: **"Everything in the Appearance. Don't touch the Style Setter."**
- Closing reflection from Eisa that anchors the new mental model: **"I consider the 'Saved Styles' to be
  Constellation theme list. I can easily switch between styles (themes) without any hassle."**
- Outcome delivered: MIG-071 shipped through §A→§K — all built-in + custom theme data wiped to plain
  default, Obsidian import removed, the Style Setter left entirely intact as the sole styling home. Eisa:
  **"Pass."**

## 3. "Conduct a universal audit"

- Eisa: **"It is time to conduct a universal audit through our audit agents. Check our dedicated audit
  agents, including UX, UI, memory leaks, etc."**
- I ran the 14-agent system; ~100 findings consolidated into `lab/reports/AUDIT-2026-06-07.md`.
- On scope of fixes, Eisa was decisive: **"Fix ALL CRITICAL + HIGH now."**
- Delivered: 1 CRITICAL (the CI Git-LFS checkout shipping pointer stubs instead of the real ONNX model) +
  13 HIGH (search hardening, 2nd-screen XSS, search caps, editor re-embed, the offline guard). A few HIGH
  items deferred with reasons (file-tree virtualization; the CSP `unsafe-inline` migration — I confirmed a
  naive removal white-screens the app, so it needs a proper hash/nonce pass, not a one-liner).

## 4. The @xenova offline break

- Eisa handed me a precise brief: the Sky View "Compute Semantic Links" used `@xenova/transformers` to pull
  `Xenova/all-MiniLM-L6-v2` from the HuggingFace CDN — a runtime network call that breaks the offline
  guarantee. Fix direction (his): either disable remote models, **or (preferred) route through the bundled
  local Rust ONNX engine and drop @xenova**. Plus: **"Verify by running the feature with the network
  disconnected — it must work, not silently fail."**
- Terminology correction, twice: I wrote "Star View"; Eisa: **"we call it the Star View"** then immediately
  **"Correction: The Sky View."** (Noted — Sky View, always.)
- First offline test *failed*: **"I clicked 'Compute Semantic Links' without internet… the button turned
  into 'Loading AI model'… 8 minutes so far."** Eisa asked me to **"Find the Loading-AI-model button state
  in the Sky View."**
- Root cause was **not** the @xenova swap — it was a pre-existing sequential `read_file` loop (one call per
  note × 7,660) running *before* embedding. Fixed with batched parallel reads.
- Re-test: **"Pass. Reading took more than a minute, embedding around 3.5 minutes. The result: 500
  connections found… All without the internet connection."** Offline guarantee proven.

## 5. "Focus on the image background"

- Eisa asked whether the 500 links should show on the graph. They were already drawn (faint dashed indigo);
  his screenshot confirmed them: **"They are already there. Focus on the image background."** — redirecting
  to the graph's flat light-gray backdrop.
- I diagnosed it live: the graph canvas is transparent, so the visible colour was the **shared panel
  surface** (`--background-secondary`) — and after the theme wipe it fell back to the plain light-gray. The
  existing "Panel background" control could change it, but only by moving every sidebar too.
- Since the desired colour was genuinely Eisa's call, I asked (one design question) what he wanted. He chose
  **"Own Style Setter control"** — a graph-only colour, decoupled from the chrome.
- Delivered: a new **Style Setter → Sky View → Canvas → Background** control (new `--skyview-bg` var),
  wired into both the full Sky View and the second-screen companion, unset = today's look. Built, Stage-0
  verified, tested. Eisa: **"Pass."**
