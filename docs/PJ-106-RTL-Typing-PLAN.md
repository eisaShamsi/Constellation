# BINDING AMENDMENTS (design-stage safety inspection — apply during Build)

**SI1-F1 (HIGH) — A4 registers callout/inline isolate ranges through EditorView.bidiIsolatedRanges but the plan does not specify HOW. That facet takes `DecorationSet | ((view)=>DecorationSet)`; getIsolatedRanges invokes the function form `i(view)` EVERY time it runs (view/index.js:1509). getIsolatedRanges is called from bidiSpans (:8469, :8473), and after any docChange all bidiCache entries are stale (fresh=false, :8858) so bidiSpans re-enters getIsolatedRanges for each line it touches. If A4 passes a function that REBUILDS the isolate DecorationSet by scanning (the natural first implementation, mirroring how bidiPlugin/calloutPlugin build their sets), the scan re-runs per-line, per-measure.**

- Failure: B2 select-page / select-all on a 200-visible-line Arabic note: drawSelection's rectanglesForRange loops every visible line calling view.bidiSpans(docLine) (:9242); each bidiSpans → getIsolatedRanges → the facet function rebuilds the whole isolate set = ~200 full scans in one measure pass (O(visible^2)). Even for a plain collapsed caret, every keystroke re-invokes the facet fn for the cursor line (stale cache). On the Boss's daily bilingual notes this is a perceptible typing/selection stall — a direct Rule-1 / INV-1 violation.
- Amendment: MANDATE the cached-field pattern in A4, verbatim: build the inline isolate marks (carrying the `bidiIsolate` spec property) ONCE per docChanged/viewportChanged inside the existing bidiPlugin/calloutPlugin update cycle, store them on the plugin instance, and expose the STORED reference via `EditorView.bidiIsolatedRanges.of(v => v.plugin(plugin)?.isolates ?? Decoration.none)`. The facet function must do zero scanning/allocation — only return the pre-built field (exactly how @codemirror/language's own bidiIsolates() backs the facet with a ViewPlugin field). Add an explicit A4-verify assertion: the facet callback performs no doc/viewport scan. Also clarify that only INLINE isolate marks go through the facet — the existing per-line `dir` LINE decorations are consumed via CSS/textDirectionAt, not this facet.

**SI1-F2 (HIGH) — A1's INV-3 safety rationale is a misdiagnosis. The plan states pure-LTR/English notes are safe because 'decoration only fires on non-base lines.' But the cost of enabling perLineTextDirection.of(true) is NOT decoration-gated: it changes textDirectionAt from a cached O(1) property read to a forced readMeasured()+getComputedStyle(tile.dom).direction, and that runs on every bidiSpans call regardless of whether any dir decoration exists on the line. Because both panes use drawSelection(), the cursor layer calls coordsAtPos(head)→bidiSpans on every collapsed-caret redraw = every keystroke, for ENGLISH notes too. Per-note gating cannot avoid it without breaking T① (an empty/English note must still present an RTL caret on Arabic-keyboard switch), so INV-3's literal 'zero regression' is unreachable and must be proven-negligible instead — but the plan would measure the wrong thing.**

- Failure: Rapid typing / key-repeat in a large pure-English note post-A1: each keystroke's drawSelection cursor redraw now performs readMeasured() (forces pending-layout flush) + getComputedStyle on the cursor line that today costs zero (textDirectionAt short-circuits to this.textDirection while the facet is off). If WebView2's forced style recalc on the large content DOM is non-trivial under key-repeat, typing latency on English notes regresses — the exact INV-3 violation — and the plan's stated 'decoration-fires' gate wouldn't detect it because it targets the wrong mechanism.
- Amendment: (1) Correct the A1 rationale: state that perLineTextDirection makes textDirectionAt do readMeasured()+getComputedStyle on every bidiSpans call, hitting English notes via the drawSelection cursor path — the cost is caret-draw-driven, not decoration-driven. (2) Make INV-1/INV-3 measurement TWO explicit, separately-signed-off gate items: a pure-English 10-char burst (INV-3 target) AND an RTL-base burst, each with a before/after latency number and a hard 'imperceptible or it doesn't ship' bar. (3) Note that gating the facet per-note is rejected because it breaks T①, so INV-3 is satisfied by measurement, not by scoping.

**SI1-F3 (MED) — A4 cites @codemirror/language bidiIsolates()'s 'built-in optimization: active only on RTL-containing lines' as its performance justification. Per the installed type docs that optimization is INVERTED for the Boss's primary case: it only restricts isolation to RTL-containing lines WHEN the editor direction is uniformly LTR; when the base direction isn't uniformly LTR (exactly what A1 establishes for an Arabic note), isolating elements are added on EVERY line. So on RTL-base notes the cited optimization does not apply, and the LTR-dominant 7,600-note test Universe never exercises the costly path.**

- Failure: On a 500-line Arabic note (RTL base) scrolled rapidly, bidiIsolates() applies isolation on all visible lines each viewport change (not just RTL lines), and the INV-1 measurement — run only against the LTR-heavy 7,600-note Universe as the plan currently specifies — reports green, so a real per-scroll-frame cost on the Boss's actual daily notes ships unmeasured.
- Amendment: Remove the 'only active on RTL lines' claim from A4's perf argument. Require the INV-1 measurement fixture to include a large (~500-line) RTL-BASE Arabic note and assert scroll-frame smoothness there specifically, in addition to the LTR Universe boot/type measurement. If the per-line isolation proves costly, scope bidiIsolates() narrowly or omit it and rely only on the explicitly-built inline isolate marks (F1's cached field).

**SI2-1 (HIGH) — Base-direction split-brain: A1 places H2 + H3 (the base-direction attributes) inside the mount-once rtlMotionCompartment, but the base authority is reconfigured elsewhere on an in-place dir change — so the two signals desync, and rollback strips the base entirely.**
