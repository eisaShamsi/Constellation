## §3. Drift Findings (11 items: 1 HIGH, 3 MEDIUM, 3 LOW, 4 NOTE)

### §3.1 HIGH — `dataview.rs` is an undocumented production consumer of the §A "preserved" helpers

**What.** §A commit message and code comments (`bases.rs:563-565`, `575-576`) claim `scan_folder`/`scan_by_tag`/`apply_filters`/`apply_sorts_fixed` are "private test infrastructure" that will be "removed alongside scan_folder / scan_by_tag / apply_filters / apply_sorts_fixed in §J's cleanup pass."

**Where.**
- `src-tauri/src/dataview.rs:6-9` (use statement importing all four)
- `dataview.rs:332, 338, 345, 354, 359` (call sites)
- `bases.rs:229` (`pub fn scan_folder`), `bases.rs:281` (`pub fn scan_by_tag`), `bases.rs:342` (`pub fn apply_filters`), `bases.rs:958` (`pub fn apply_sorts_fixed`) — all `pub`, not `pub(crate)`.

**Why drift.** Neither the Architect doc, Plan doc, nor `bases.rs` comments mention `dataview.rs` as a consumer. The DQL/Dataview command (a separate IPC surface from Bases) remains on the filesystem-walking implementation post-§A. The §J planned cleanup would `pub fn` → delete the helpers, breaking the Dataview Tauri command at compile time.

**Impact.** Current state (§G) is correct — Dataview still works as before. The hazard is in §J: a future maintainer executing the "delete the dead helpers" plan would break the build.

**Recommended action.** Block §J helper deletion until either (a) `dataview.rs` is migrated to SQL via a parallel MIG-055, or (b) the helpers are explicitly scoped to remain. Recommend the §J PCS commit include a Plan-doc amendment at §6: *"`scan_folder` / `scan_by_tag` / `apply_filters` / `apply_sorts_fixed` are NOT deleted in MIG-054. They continue to serve `src-tauri/src/dataview.rs`. A follow-up MIG-055 should migrate Dataview to SQL; until then these helpers remain `pub fn`."* Open PJ-NNN for that follow-up migration.

### §3.2 MEDIUM — Folder LIKE patterns inlined into SQL (not parameterized)

**What.** Folder source path prefixes are escaped (`'` → `''`) and inlined into the SQL string rather than passed as `?` bound parameters. Architect §5.2/§5.3 implies all values parameterized.

**Where.** `bases.rs:735-746`. Comment at `bases.rs:709` acknowledges: *"path patterns are inlined with single-quote escaping (LIKE patterns can't be parameterized cleanly)."*

**Impact.** SQLite LIKE patterns CAN be parameterized via `LIKE ? || '%'` — the inlining is a convenience, not a necessity. `library_path` comes from `libraries.json` (user-controlled at library-add time, not remote/untrusted), so the practical injection surface is low. But the contract is undocumented.

**Recommended action.** Architect amendment at §J PCS noting the inlining decision + the escaping invariant: only single-quote escaped; embedded `\`/`%`/`_` pass through (acceptable for paths). Or refactor to parameterize via `LIKE ? || '%'` in a §B.1 / §J cleanup.

### §3.3 MEDIUM — Body-tag matching applies Arabic normalization that OLD `scan_by_tag` did not

**What.** §B's tag source body matching uses `body_text` (Arabic-normalized at write time per `bases.rs:765-768` comment) AND normalizes the user's tag via `arabic::normalizer::normalize_stripped`. The OLD `scan_by_tag` (`bases.rs:317`) does `content.contains(&format!("#{}", tag_clean))` against raw file content with NO Arabic normalization.

**Where.** New: `bases.rs:784-798`. Old: `bases.rs:312-318` (preserved helper).

**Impact.** Behavioral semantics change for Arabic users — a search for `#الإمارات` will now find body text containing `#الْإمارات` (with tashkeel diacritic) because both sides normalize. The OLD behavior would not match. This is arguably BETTER UX but is a documented divergence the Architect/Plan docs don't promise.

**Recommended action.** Architect amendment at §J listing this as Acknowledged Divergence #2 (the case-sensitivity divergence from §B is #1). The integration test `equivalence_tag_source_body_only` covers ASCII tags; an Arabic-tag body-match equivalence test would be a §J addition that asserts the divergence is intentional.

### §3.4 MEDIUM — Concurrent cell-edit race (file write is source of truth; reconciliation is eventually consistent)

**What.** §E's `update_note_meta_property_immediate` uses `json_set` to merge ONE key. If two cell-edits fire in close succession, the second's file write happens AFTER the first edit's note_meta merge but BEFORE the file-watcher debounce reads the file. The watcher then re-parses and UPSERTs the full `properties_json` based on the file content — which is correct (file is source of truth).

**Where.** `bases.rs:1094` (file write) + `bases.rs:1112` (immediate note_meta merge) + `search.rs:3394-3414` (file-watcher UPSERT).

**Impact.** Architect §8 risk #4 mitigation claims *"the file-watcher's re-parse is idempotent (content_hash matches → no-op)."* That mitigation assumes one edit; with two consecutive edits the content_hash differs and the watcher DOES re-parse. The watcher's UPSERT correctly reflects the file (which has both edits). No data loss. The race only affects the brief window when an intermediate `note_meta` state could be queried — a stale read, not a corrupted write.

**Recommended action.** Architect §8 risk #4 wording refinement at §J: *"The file is source of truth; the immediate merge gives instant UI, the watcher write reconciles to truth. If two edits race, the file content wins — by design."*

### §3.5 LOW — `update_note_property` asymmetric vs `validate_base_path`

**What.** `update_note_property` (`bases.rs:1078-1087`) accepts paths within registered libraries only. `validate_base_path` (`bases.rs:25-55`) ALSO accepts paths within the active universe's `.constellation/bases/` directory. Asymmetry is undocumented.

**Where.** `bases.rs:1078-1087` vs `bases.rs:25-55`.

**Impact.** Correct behavior — a Note shouldn't be edited via `update_note_property` if it's a `.base` file in `.constellation/bases/`. The asymmetry isn't a bug; it's a deliberate scope boundary that isn't called out in Architect §3.

**Recommended action.** One-line comment at `bases.rs:1078` documenting the deliberate divergence.

### §3.6 LOW — Error messages embed raw SQL strings

**What.** `query_base_with_conn` and `detect_columns_sql` `.map_err(...)` paths include the raw SQL string in user-facing error messages.

**Where.** `bases.rs:511` (`format!("Failed to prepare query_base SQL: {}\nSQL: {}", e, sql)`); `bases.rs:917` (same shape for `detect_columns_sql`).

**Impact.** Frontend toasts can display multi-line SQL. Bad UX, mild observability/info-leak issue. Constellation is local-first so no remote attack surface, but ugly.

**Recommended action.** Strip the SQL fragment in release builds OR keep for dev observability with a `#[cfg(debug_assertions)]` gate. Document decision either way at §J.

### §3.7 LOW — `build_source_where` "vault" branch is dead path post-modernize

**What.** §D's `modernize_legacy_vault_source` translates `"vault"` source at parse time. The `"vault"` branch in `build_source_where` (`bases.rs:802-819`) is now a defensive fallback for programmatic BaseSource construction.

**Where.** `bases.rs:802-819` + `bases.rs:1438-1458`.

**Impact.** The defensive branch is sensible (e.g., tests, future feature work that bypasses parse). The contradiction with §5.7 ("save path never writes `vault` again") is subtle — saves never produce `vault`, but builds can. Code comment at `bases.rs:1431-1433` documents the intent.

**Recommended action.** Architect amendment one-liner at §J: *"The `build_source_where` `vault` branch is a defensive fallback for programmatic construction; parse-path retirement is via `modernize_legacy_vault_source`."*
