### [APP-KILLER] `src/lib/components/PropertyEditor.svelte:852` — silent-data-loss  *(frontmatter-property-writes)*

PropertyEditor pushes its WHOLE `editableProps` snapshot into the note model on every debounced save, but its `properties` prop is derived from `tab.content`, which the model-based prop writers (saveTabContent / addTagToNote) never update and never notify — so a later panel edit replays a stale full-props array and silently erases frontmatter another writer already persisted.

**Silent failure scenario.** Note N is open with the Properties panel visible; its frontmatter has no `tags` key. The user right-clicks N in the file tree and picks Add tag → `addTagToNote` (+layout.svelte:6483) takes the OPEN branch: composeNoteModel → addTagToProps → `saveTabContent`. saveTabContent calls `editNoteProps` (store.ts:1346) which REPLACES model.props with props+tags, composes, and writes `tags:` to disk. It deliberately does NOT touch `tab.content` ("Do NOT update the store during autosave") and — unlike addLinkToNote, which added `reloadTabsFromDisk` for exactly this reason (store.ts:1101-1108) — it never reloads the tab. NoteEditor's `parsed` is `$derived.by(() => $openTabs.find(...) → parseFrontmatter(ct.content))`, so with no `openTabs.update()` the panel's `properties` prop is unchanged; PropertyEditor's sync `$effect` compares the same JSON snapshot and skips the resync, leaving `editableProps` without `tags`. The user now edits any unrelated property in the panel → debouncedSave → `saveTabContent(tabId, filePath, editableProps, body)` at :852 → `setProps` overwrites model.props with the STALE array (no tags). composeFrontmatter then diffs base.props (the OPEN-TIME projection, which also has no tags) against the new props: no ADD, no REMOVE, and the CST is re-parsed from `m.base.rawYaml` — the open-time bytes that predate the tag. The composed content simply has no `tags:` line, and it is written to disk. The tag is gone from the .md with no error, no dirty flag, no conflict, and the re-parse is clean so nothing downstream notices. The same loss runs in both directions between the two simultaneously-mounted PropertyEditor instances (NotePane's embedded one at NotePane.svelte:1639 and the right-sidebar one at +layout.svelte:8990) — both bind the SAME tabId and both overwrite model.props wholesale from their own stale snapshot. The onDestroy flush at PropertyEditor.svelte:511 replays the identical stale array.

### [APP-KILLER] `src/lib/components/PropertyEditor.svelte:851` — content-loss  *(reactivity-concurrency)*

Two PropertyEditor instances (NotePane-embedded + right-sidebar) are mounted for the SAME tabId at once, each holding its own `editableProps` snapshot; a save writes the store tab's content by DIRECT non-reactive mutation, so neither instance ever re-seeds from the other's edit — and the second one to save replaces the model's whole props array with its stale snapshot, durably reverting the first edit on disk.

Disk now has `stage: sapling`.
(2) Because `openTabs` is a plain `writable` and no `.update()` was called, `$openTabs` never emits, so the sidebar instance's `properties` prop never re-derives and its re-seed `$effect` (line 360) never fires. (3) The user now adds a tag in the SIDEBAR Properties panel. Its `debouncedSave` fires with its stale array: `editNoteProps` replaces the model's props with `{stage: seed, …, +tag}`. Because the model's G4 write-base (`m.base.props`, captured at open) also says `seed`, `composeFrontmatter` sees NO diff for `stage` and emits the base's original bytes — so the durable write puts `stage: seed` back on disk.
Result: the stage edit is gone from disk AND from the model, with no error, no conflict sidecar, no save-health banner. Worse, the in-note panel still displays `sapling` (it is not re-seeded either), so the UI actively hides the loss until the note is closed and reopened. Same loss in the reverse order, and for any frontmatter key (tags, sources, typed-link properties, review fields).
