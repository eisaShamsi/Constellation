## Register #0 — [HIGH] `src/lib/libraries/store.ts:1130` (notemodel-ownership / content-corruption)

**Summary.** reloadTabsFromDisk matches incoming paths to open tabs with raw `t.path === fp` (also lines 1163 and 1184), while its two sibling arbiters of the same concern — openNoteTab dedup (:3287) and adoptExternalChangeIntoTabs (:1321/:1362) — were normPath-fixed on 2026-08-01 for exactly this class. A form-drifted open referrer is silently skipped by the rename-cascade reload.

**Silent-failure scenario.** User renames note 'Old' → 'New'. The Rust walker rewrites [[Old]]→[[New]] in referrer X on disk and returns X's path in result.rewritten in its canonical form (backslash / its own case / NFC form). X is open in a tab whose stored path differs in separator, case, or NFC form (the premise the 2026-08-01 fix comments and PJ-092 H1's NFC-folding assert as real for this exact path pair). reloadTabsFromDisk's `tabs.some(t => t.path === fp)` misses → returns [] → X's model keeps the pre-cascade body with [[Old]]. Cascade writes are watcher-suppressed, so adoptExternalChangeIntoTabs never fires to heal it, and the defence-in-depth cascade:rewrote listener (+layout.svelte:3850) calls the SAME broken matcher. Model is clean so nothing writes yet; the moment the user types one character in X, the 1500ms debounced save composes the stale body and durably writes [[Old]] back over the cascade's [[New]] — the rewrite is reverted on disk, the link now points at a note that no longer exists, reindex runs on the reverted content so the index agrees with the wrong disk, and no error, banner, or journal marker fires anywhere.

**Verification (why CONFIRMED).** Every link in the chain verified in source. (1) reloadTabsFromDisk matches tabs raw — store.ts:1130 `t.path === fp`, :1163/:1184 `byPath.get(t.path)` — while its two siblings arbitrating the same tab-vs-incoming-path concern were normPath-fixed 2026-08-01: adoptExternalChangeIntoTabs (:1321/:1337/:1362, whose comment records the REAL incident this mechanism caused: "made every Windows tab miss... the next keystroke's save overwrote the external edit") and openNoteTab dedup (:3287). (2) The form-divergence premise is asserted by the caller itself: +layout.svelte:7573, three lines above the reloadTabsFromDisk call at :7587, folds this exact path pair (tab-derived excludedPaths vs result.rewritten) through normPathLC + NFC because "a leak that reaches here differs by NFC/NFD"; result.rewritten is PathBuf::to_string_lossy from the Rust walk (libraries.rs:7900), OS-native form. (3) No healer: cascade writes are watcher-suppressed (libraries.rs:2883; +layout.svelte:5704 states "watcher-suppressed, so no external-change adopt could heal it"), and the defence-in-depth cascade:rewrote listener (:3850) calls the same broken matcher. (4) The terminal write is unblocked: WRITE_GATE_ENFORCE = false (write_gate.rs:41) — a WouldRefuseStale verdict journals in shadow mode and the write proceeds (:435-441), so the first keystroke's debounced save durably reverts [[New]] to [[Old]] on disk and reindex follows the reverted content. (5) The skip is total and silent: a form-drifted tab misses the :1130 filter, is absent from byPath, so it is neither adopted nor refused-dirty — no banner, no conflict sidecar, no user-visible signal; even without typing, the open tab displays pre-cascade content diverging from disk all session. Severity HIGH, not APP-KILLER: requires the form-drifted-path precondition (edge population, but one the codebase paid two fixes and an NFC belt for), and the loss is the link-rewrite reversion in one referrer (a wrong link that looks right, index agreeing with the wrong disk) plus display/disk divergence — not user prose. Minor correction to the candidate: the write-gate journal may record a shadow WouldRefuseStale line if the save carries a baseline expectation, so "no journal marker anywhere" is slightly overstated — but nothing is surfaced to the user, which is the silence criterion.

## Register #1 — [HIGH] `src/lib/libraries/store.ts:1130` (editor-lifecycle / content-loss)

**Summary.** reloadTabsFromDisk matches open tabs by RAW string equality (t.path === fp) while its sibling adoptExternalChangeIntoTabs was explicitly fixed to match on normPath (store.ts:1321-1322, 2026-08-01 inspection) — a tab whose stored path differs from the caller's path in separator form, drive-letter case, or NFC/NFD is silently filtered out of the force-adopt, so the open note's model never learns about a rewrite this app just made to its file on disk.

**Silent-failure scenario.** A note is open in a tab whose stored path uses '/' separators (the codebase documents this occurring: the openNoteTab dedup at store.ts:3285-3287 was fixed 2026-08-01 precisely because 'a mixed-separator stored path' slipped past raw comparison; session-restored tabs reuse saved.path verbatim from session.json). The user renames another note; the wikilink cascade walker rewrites this open note's file on disk ([[Old]] -> [[New]]) and handleRenameComplete calls reloadTabsFromDisk(result.rewritten) with the Rust walker's backslash-form path. Line 1130's strict equality finds no matching tab, the target is dropped, the function returns [] (no refusal warning, no conflict, no journal marker) — and the defence-in-depth cascade:rewrote listener (+layout.svelte:3850) funnels into the same filter and misses identically. The cascade's write is watcher-suppressed (§3-redo.2), so the watcher adopt path never delivers it either. The clean in-memory model now permanently holds the pre-rewrite body while disk holds the rewrite. The next time the user types one character in that note, the model goes dirty and the 1500ms debounced save composes the pre-rewrite body + keystroke and durably writes it over the walker's rewrite — the [[link]] silently reverts to a title that no longer exists, with no error, no banner, no sidecar. The same shape reverts a task-checkbox toggle (toggleTaskReconciled, store.ts:1462) and a structural resolve (store.ts:6239) when the panel-supplied path form differs from the tab's stored form. Fix shape: normalize both sides at line 1130 (and the byPath lookups at 1163/1184, plus focusPathAmong's fold at store.ts:1100, which handles case/separators but omits .normalize('NFC') despite PJ-092 H1 naming NFC divergence 'the headline hazard'), matching the invariant adoptExternalChangeIntoTabs already enforces.

**Verification (why CONFIRMED).** Verified in code: store.ts:1130 filters cascade-reload targets by RAW equality (t.path === fp), and the dirty-refusal loop (1163) and force-adopt (1184) stay raw — while its sibling adoptExternalChangeIntoTabs (1321-1322, 1356-1362) was explicitly fixed on 2026-08-01 to normalize both sides, with comments recording that the unnormalized compare "made every Windows tab miss… and the next keystroke's save overwrote the external edit," and the openNoteTab dedup (3287) confirming mixed-separator stored tab paths occur in reality. The caller handleRenameComplete (+layout.svelte:7587) passes result.rewritten verbatim — Rust-native to_string_lossy paths (libraries.rs:7902) — yet three lines earlier its own PJ-092 belt folds both sides with normPathLC+NFC before comparing the same two path populations, an in-function admission that raw comparison of these strings is unsound. Every backstop funnels into the same miss: the cascade:rewrote listener (3850) calls the same function; the watcher is suppressed for cascade writes (§3-redo.2, listener comment 3826-3829); a leaked watcher event hits isCascading (1364) which defers back to the force-adopt that missed. The final overwrite is silent: the missed tab yields an empty return (no refusal warn/journal at 7591), the clean model keeps the pre-rewrite body, and the next keystroke's debounced save is detected as WouldRefuseStale by the write gate but WRITE_GATE_ENFORCE=false (write_gate.rs:41) — shadow mode writes it anyway and write_note returns Ok(()), so no banner, sidecar, or error ever surfaces. Disk's [[New]] silently reverts to [[Old]] — a wikilink to a nonexistent title. Refutations attempted and failed: forms-always-match (contradicted by the codebase's own confirmed 2026-08-01 findings on the same tab store), watcher-recovery (suppressed by design), gate-blocks-stale (shadow, off), symmetric-miss-protects-dirty (true, but the stale-clean-adopt-miss failure stands). Severity HIGH not APP-KILLER: the loss is the cascade rewrite in an affected open note (silent link-integrity corruption), not the user's typed content, and requires a path-form-divergent tab — the same band the sibling finding was fixed at. Fix shape as the candidate states: normalize (normPath + case fold + NFC, matching the caller's own belt) at 1130/1163/1184 and add .normalize('NFC') to focusPathAmong (1100).

## Register #2 — [MED] `src-tauri/src/libraries.rs:9372` (rename-move-delete-gate / index-divergence)

**Verification (why CONFIRMED).** Verified in code: delete_path (libraries.rs:9372) authorizes via the FEDERATED resolver validate_path_in_any_library (line 793) and guard_no_foreign_library_under (line 597) only refuses foreign LIBRARY ROOTS at/under the path (stranded_library_names, line 568) — a plain linked-universe note passes both. ## Register #3 — [MED] `src/lib/editor/noteModel.ts:493` (notemodel-ownership / content-loss)

**Summary.** The manual-open recovery lane (markRecoveredFromNet, called from openNoteTab at store.ts:3503) has no arbiter for an external disk edit that landed while the app was closed: the net never stores the stash-time disk bytes, so a moved-on disk is indistinguishable from the unchanged pre-save disk, and the recovered content silently overwrites the external edit with no .conflict sidecar.

**Silent-failure scenario.** A save fails on a locked .md (net holds V2, disk holds V1). App closes. A sync agent (Syncthing / second device — the exact actor PJ-207 §15 names for the restore lane) updates the file to V3. User reopens the note by clicking it: resolveNoteContent finds the identity-proven real-work net entry, the screen shows V2, markRecoveredFromNet makes the model dirty with baseline=V3. No watcher event will ever fire for V3 (it predates the open), so the .conflict machinery — which only arbitrates incoming events on adoptExternalChangeIntoTabs — never runs. The first tab switch or app close flushes the dirty model: V2 is durably written over V3. The external edit is gone from disk with no sidecar, no banner (saveHealth did not survive the restart), and no journal record. The restore lane got netUnsaved + adoptDisk-refusal protection for this scenario; the manual-open lane has none for changes predating the open.

**Verification (why CONFIRMED).** Verified end-to-end in code. resolveNoteContent (store.ts:3122) admits in its own PJ-181 comment that every net-acceptance check passes for an externally-edited note (cid is identity, not freshness), and the staleSnapshot cure only covers snapshot===true entries — a failed-save entry is stashed by saveUnchained with no snapshot flag and no stash-time disk bytes (WriteAheadEntry stores a flag "rather than a copy of the baseline bytes, deliberately", store.ts:314). markRecoveredFromNet (noteModel.ts:484) then sets diskBaseline to the CURRENT disk bytes (V3) and dirties the model, which makes diskDiffersFromBaseline false for V3 forever — both conflict arbiters (store.ts:1176, 1374) are structurally blind to the pre-open external edit, and no watcher event exists for it (closed note / predates the open). The flush path has no freshness check, the frontend writeNote passes no Expectation, and the Rust write gate is shadow-only (WRITE_GATE_ENFORCE=false, write_gate.rs:41) with §B2 identity self-attestation passing (same note). closeTab (store.ts:3869) explicitly proceeds on a failed flush, naming reopen as the recovery route — so the lane is reachable with routine actions: failed save on a locked file → close tab → sync agent writes V3 → click the note → first nav/close flush durably writes V2 over V3. No .conflict sidecar, no banner (the successful write clears the red banner), no journal anomaly. The restore lane's netUnsaved protection guards only future watcher events and is never set on this lane. Silent loss of the external edit, contradicting the system's own dirty+moved-disk contract (.conflict sidecar) everywhere else.

**Verification (why CONFIRMED).** The exact-match is real and the drift precondition is both creatable and permanent. Severity stays MED rather than HIGH because the failure needs the pre-existing path-form drift (external case-only rename, or the NFC/NFD form drift the code itself has witnessed), destroys the cascade's rewrite (a broken link) rather than user-typed content, and a later tab reopen re-reads disk.

## Register #28 — [LOW] `src/lib/components/FocusPane.svelte:267` (freeze-and-leaks / freeze-hang)

**Summary.** FocusPane's EditorView.updateListener calls update.state.doc.toString() plus a full-text regex word-split on EVERY keystroke — O(N) per keystroke on the hot path, the exact pattern NotePane's own listener bans by comment ('do NOT call doc.toString() here — it's O(N) on every keystroke and causes progressive lag') and CLAUDE.md Rule 1 forbids. FocusPane is the speed-first surface, so it is the one place this hurts most.

**Silent-failure scenario.** User opens a large note (say 500KB–1MB of accumulated capture) in Focus mode and types a burst: each keystroke serializes the entire rope to a String and then splits the whole text on /\s+/ to recount words — two full-document passes per character. Typing latency grows with document size until keystrokes visibly lag the screen; no error anywhere, it just feels like the app got slow. Silent degradation of the one surface whose design contract is 'capture ideas fast'.

**Verification (why CONFIRMED).** Verified at FocusPane.svelte:265-274: the updateListener runs doc.toString() + trim().split(/\s+/).filter() on EVERY docChanged with no debounce or size guard, then hands the full string to onchange. NotePane.svelte:583-584 contains the exact ban comment the candidate cites ("do NOT call doc.toString() here — it's O(N) on every keystroke and causes progressive lag"), proving the lag is empirically known in this app, not theorized. Benchmarked: split+filter alone costs 4ms/keystroke at 500KB and 8ms at 1MB (before toString itself). Investigation found the defect is WORSE than the candidate states: +layout.svelte:9368 passes the string to editNoteBody per keystroke, hitting noteModel.ts setBody's STRING path (toText = full O(N) rope rebuild per keystroke) in direct violation of that function's own documented invariant (noteModel.ts:259-265: "the STRING form of setBody is ONLY the cold flush/teardown pushes... never the per-keystroke Text path... the keystroke hot path stays O(1)"). Total synchronous per-keystroke cost at 500KB-1MB reaches/exceeds the 16ms frame budget plus heavy GC churn — perceptible typing lag on the speed-first surface, with no error surfaced and no self-correction. No refutation condition holds: path is reachable (open large note in Focus, type), ungated, silent. Severity stays LOW: pure progressive degradation — no data loss, no divergence, no actual hang — and perceptibility requires an atypically large note (hundreds of KB+).
