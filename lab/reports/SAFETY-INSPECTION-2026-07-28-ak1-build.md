### [APP-KILLER] `src/lib/editor/yamlDoc.ts:188` — content-loss  *(frontmatter-property-writes)*

A YAML BLOCK SCALAR (`key: |` / `key: >`) is the third unguarded frontmatter shape: store.parseFrontmatter projects it as an ordinary EDITABLE text property whose value is the literal header character `|`, and immutableBlockKeys only treats maps and seqs-of-maps as immutable — so editing or deleting that row splices the whole multi-line block out of the .md with no error.

**Silent failure scenario.** A note (typical of an imported Obsidian vault, and a shape the Rust index reader explicitly supports — see the collect_block_scalar branch at src-tauri/src/search.rs:4966 and tests/fixtures/g4_scalar_forms.json) has:
---
title: X
abstract: |
  line one
  line two
tags:
  - a
---
The Properties panel renders a row `abstract` whose value box literally reads `|` (detectPropertyType at store.ts:169 returns 'text'; isEmpty is false so it is not even flagged empty). The user, seeing a property that looks like garbage, types the real abstract — or clicks the row's delete button. debouncedSave (PropertyEditor.svelte:840) -> saveTabContent -> setProps -> composeFrontmatter. immutableBlockKeys (yamlDoc.ts:188) computes `isMap(v) || (isSeq(v) && !all scalars)`; a block scalar is an isScalar node, so `abstract` is NOT immutable. In the SET branch (yamlDoc.ts:365) the CST token type for a block scalar is `block-scalar`, not `scalar`, so the in-place setScalarValue is skipped and control falls to the else: items.splice(idx,1) + append `abstract: hello`. Verified by running the real algorithm against yaml@2: input `title: X / desc: | / line one / line two / tags: - a`; editing desc produced `title: X\ntags:\n  - a\ndesc: hello`, and deleting the row produced `title: X\ntags:\n  - a`. In both cases `line one`/`line two` are gone from the .md, the write is durable, the result re-parses without errors, and nothing surfaces. Same class as the PJ-136 nested-map fix and the 2026-07-24 seq-of-maps fix (both of whose in-code comments state the rule: when we cannot round-trip the bytes, render READ-ONLY WITH A SUMMARY) — block scalars were never brought under it, in either the projection (store.ts:2041-2056, which has no block-scalar branch) or the write-path refusal.

**Silent failure scenario.** renameItem() flushes the model at :3823-3826 (model now clean, renameFlushOk=true), then awaits `invoke('rename_item')` (:3833) and `readNote(effectivePath)` (:3869), then unconditionally calls openNoteModel(t.id, effectivePath, fresh) at :3879 with reloadVersion++ at :3889. The caret is now IN the body, so the user immediately types 'the next sentence'. The identical hazard is explicitly recognised and GUARDED at the sibling site drainCidEnsure (store.ts:2841: 'its unconditional model re-seed would discard keystrokes typed during the awaits above (markCascading blocks saves, not typing)' — it checks isNoteDirty(t.id) before openNoteModel); renameItem never got that guard. Fix shape: re-check isNoteDirty(t.id) immediately before :3879 and fall back to repathNoteModel (keep the user's model, do not clear its net), mirroring drainCidEnsure.
